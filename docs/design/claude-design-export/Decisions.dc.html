Breach Scan — design system

Decisions made, not specified

  1. Font: Source Sans 3 for everything, including numerals in the summary tiles — one family, no separate display face.
  2. Color base is cool-neutral; brand/accent hue sits at 200° (blue) for calm, 35° (burnt orange, not red) for urgent, same chroma and lightness family so the two tone sets read as siblings.
  3. Accent/tone-accent colors are deliberately darker (L≈32–42%) than a typical UI blue, so the same color works as button fill (white text) and as standalone link/text color without a second, separate "text-safe" shade.
  4. Row expand/collapse and the urgent count-up are implemented as real interactions in the deliverable, not static mockups, so their motion and end states can be checked directly.
  5. The "accounts exposed" summary tile is the element that counts up on the urgent variant — the brief calls out a counting number but doesn't say which one; the tile was the most natural home since it already exists as a value.
  6. Landing page and confirmation copy (headline, trust points, next steps) is original copy, since the brief specified exact strings only for the result screen.
  7. Given the volume of frames implied (2 variants × 3 widths × 5 states, repeated per screen), each screen shows every state as a frame, but width reflow (390/768/1280) is fully shown for the primary/default state, with secondary states shown once at 390 — states like "loading" or "server error" don't change their internal layout across widths, only their container does, which S-3's reflow notes already cover.
  8. The signup form's password-leak count ("3,120,000 leaks") and the experiment's lift numbers are illustrative — swap for live values from HIBP and the analytics pipeline.
  9. Admin's disabled Save button uses a light grey fill with a visible border and dark grey text (4.5:1+), rather than the previous washed-out blue, so "saving" reads as an active, expected state rather than a bug.
  10. Semantic landmarks (header/main/nav) are shown once per component instance for documentation purposes; a shipped page would have exactly one of each — this spec mounts many instances of each screen side by side to compare states.
